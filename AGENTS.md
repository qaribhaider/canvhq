# CanvHQ — project instructions

CanvHQ is a self-hostable end-to-end encrypted whiteboard built on `@excalidraw/excalidraw`. It is free and open source, with no commercial offering, and it is being prepared for a public repository. The code is held to a senior professional standard: clear structure, honest naming, no dead paths, and no reinvented wheels.

This is the single canonical instruction file for the repository. `CLAUDE.md` imports it, so every tool reads the same content from one place.

## Project-specific override of the global "Surgical Changes" rule

The global guideline "touch only what you must, clean up only your own mess, don't remove pre-existing dead code unless asked" **does not apply in this repository**. It is replaced by the rule below.

**Code quality is a launch requirement here, not a preference.** Work in this repo is expected to leave the surrounding code better than it was found, within the blast radius of the task at hand. Specifically:

- Structural and code-quality problems found in a file you are already working in are in scope, and should be fixed rather than worked around. That includes dead code, unused dependencies, duplicated logic and inconsistent error handling.
- Code that duplicates a library the project already depends on should be collapsed onto that library. Do not reimplement auth, validation, state management, HTTP clients or crypto primitives that a dependency already provides.
- Prefer the project's own shared layers over inline alternatives: `frontend/src/api/client.ts`, `frontend/src/lib/crypto.ts`, the backend `src/access/` module, the Zod DTOs. A page or service that hand-rolls what a shared layer already does is a defect.
- Removing dead code is expected once identified, not optional.

The scope boundary still applies in one direction: do not start a broad refactor of files the current task does not touch. Quality fixes belong in the blast radius of the work, and `local/PLAN.md` decides where the wider restructures happen and in which phase.

## Hard rules (from the PRD)

These are not negotiable, and the override above does not relax them:

- **The server must never see plaintext canvas data or keys.** All encryption and decryption happens in the browser via Web Crypto. Only names and titles (workspace, project, board) are stored unencrypted.
- **Frontend and backend stay fully decoupled.** No shared code or types, no monorepo tooling.
- **The data hierarchy is flat.** `Workspace (Better Auth Organization) -> Project -> Board`. No nested folders.
- **OAuth sign-in only.** Google is the supported provider; GitHub and Microsoft work in the code but are deliberately undocumented and untested until after launch (see `local/TODO.md`); GitLab is not supported. No email/password, by design. Production refuses to boot without a provider configured (or `DEMO_MODE=true`). No real email sending: invitations are copy-paste links.
- **Phase 1 is single-player.** No WebSockets, Yjs or CRDTs.
- **Use the libraries the project already depends on.** Better Auth stays: it owns sign-in, the session model, the organization and member model, and the OAuth flow. Do not replace it, and do not build a parallel home-grown equivalent alongside it. The same applies to CASL for authorization, Zod for validation, TanStack Query for server state and Excalidraw for the canvas.
- **UI uses shadcn primitives over one token source (`index.css`), light-only; never write an arbitrary hex class.** (`frontend/components.json`) with Tailwind and Lucide icons.

## Commands

`backend/` and `frontend/` are independent projects (each has its own `package.json`, `node_modules` and `pnpm-lock.yaml`); the root `package.json` only proxies to them. **Use pnpm**, pinned by the `packageManager` field to the exact version in the root `package.json` — do not use npm, and do not add a root `pnpm-workspace.yaml`, which would couple the two projects.

npm run build            # frontend then backend

# Backend (cd backend)

npx vitest run -t "test name"                      # single test by name
pnpm run test:integration              # real-Postgres integration specs in test/integration/*.int-spec.ts (requires `docker compose up -d db storage`, the object store only for the `demo-wipe` spec; override DB with TEST_DATABASE_URL, store with TEST_S3_ENDPOINT)
npm run lint                           # oxlint
npx prisma generate && npx prisma migrate dev --name <change>   # after editing prisma/schema.prisma

# Frontend (cd frontend)

Prettier may need a second `format` pass on a few files before `format:check` is clean, because of a known member-chain quirk. Run `pnpm run format` twice.

## Architecture

### E2EE key hierarchy (frontend `src/lib/crypto.ts`, `src/context/KeyContext.tsx`)
Each layer wraps the one below; only wrapped keys are sent to the backend:
1. User passphrase → PBKDF2 (600k iterations) → KEK, which wraps the user's RSA-OAEP private key (`User.wrappedPrivateKey`, `User.publicKey`).
2. Org key (AES-GCM) wrapped with each admin's public key → `Member.encryptedOrgKey`.
3. Project key wrapped with the org key (`Project.encryptedProjectKey`) or with an assigned member's public key (`ProjectMember.encryptedProjectKey`).
4. Board key wrapped with the project key → `Board.encryptedBoardKey`. The board payload is AES-GCM encrypted with it and stored in S3 at `boards/{boardId}/v{keyVersion}.bin`.
5. Older project keys wrapped under newer ones (`ProjectKeyHistory.encryptedKey`), allowing keyholders to walk backward through history entries to open boards created under earlier generations.
6. Encrypted image files wrapped with the board key stored at `boards/{boardId}/v{keyVersion}/files/{fileId}.bin` (AAD `canvhq/v1/board-file/{boardId}/{boardKeyVersion}/{fileId}`).
Every wrapped key and payload is a v1 envelope (`frontend/src/lib/crypto-format.ts`): `0x01`, a header of big-endian key versions and revision, then the body. The versions and the board/project/workspace/person ids (and revision on board payloads, and file id on board files) are also in the AES-GCM additional data or the RSA-OAEP label, so a blob only opens in the place it was made for. The browser chooses the resource ids at creation; the server stores the current versions (`keyVersion` on Organization, Project and Board) and refuses a stale board creation (409). Server replay of older valid board payloads is detected on devices that have seen a newer version via local revision tracking in IndexedDB (a brand new device with no local history cannot detect an initial replay). `Board.revision Int @default(0)` increments on every successful payload write; `PUT /api/boards/:id/payload` requires header `x-board-revision` matching the server revision (or returns 409 `BOARD_CONFLICT`), and the payload header revision must equal `current + 1`. Board files are uploaded via `PUT /api/boards/:id/files/:fileId` (8MB cap per file, total board storage <= 50MB, at most 100 files referenced per canvas in `x-board-file-ids`, an empty header meaning "no images left"). A re-key save first re-encrypts and uploads every file at the new key version (the file route accepts that upload at the project's key version, for files the board already holds); the server checks each copy exists before it moves the rows and queues the old objects, and the browser keeps the old key when it cannot re-encrypt a file. When an Admin is demoted or removed, rotation proceeds in strict order: the workspace key rotates first (rewrapping all project keys under the new workspace key generation), then due projects rotate under it. Project key rotation is refused with 409 while workspace key rotation is pending.

Unlocked private keys are cached as non-extractable `CryptoKey`s in IndexedDB (`src/lib/key-store.ts`). Invitations carry no keys: they may pre-assign projects, and each grant starts pending (`ProjectMember.encryptedProjectKey = null`) until a keyholder completes it explicitly. Public share links (`PublicBoardView`, backend `public-boards.controller.ts`) use a server token plus a board key in the URL hash fragment, which never reaches the server.

### Backend (`backend/`, NestJS 12, ESM)
- ESM with `"type": "module"`: relative imports must use the `.js` extension.
- Env is validated at boot by `config/env.schema.ts`. Request validation uses a global `ZodValidationPipe`, so DTOs are Zod schemas (`nestjs-zod`), not class-validator. Swagger is at `/api/docs`.
- Auth: Better Auth with the organization plugin (`src/auth/auth.ts`). The global `SessionGuard` resolves the session from request headers; the active org comes from the `active-organization` header (set by the frontend via `activeOrgId`), the `:id`/`:slugOrId` path parameter, or the session.
- Authorization lives in one module, `src/access/`. `roles.ts` owns the vocabulary (`owner | admin | editor | viewer` at workspace level, `admin | editor | viewer` at project level, enforced by database `CHECK` constraints). `abilities.ts` is the single CASL rule table: owners and admins are workspace administrators and project admins; everyone else has exactly their project role, and a workspace editor or viewer with no project grant has no access to that project. `AccessService` resolves the caller's membership once per request and the global `AccessGuard` checks the route's `@Access({ scope, can })` against it. A non-public route with neither `@Public()` nor `@Access(...)` is refused; the route-inventory integration test fails when one appears. Services receive the resolved `Access` and never compare role strings.
- Workspaces are created only through `POST /api/workspaces`. One transaction writes the organization, the Owner membership (holding `encryptedOrgKey`) and the first project (its workspace-wrapped key plus the creator's own grant); all three wrapped keys are required, and a failure at any step leaves nothing behind. The route applies `canCreateWorkspace`: a user with no memberships may create their first workspace; after that only an Owner or Admin may create more. Editor-only and Viewer-only users get a 403; the operator's per-account limit (batch 18) extends that one function. Better Auth's own `/organization/create` is disabled.
- Every project and board is created with its wrapped key: `POST /api/projects` requires a browser-chosen `id`, `encryptedProjectKey` and `creatorEncryptedProjectKey`; `POST /api/boards` requires a browser-chosen `id`, `encryptedBoardKey` and the `projectKeyVersion` it was wrapped under (400 without, 409 if stale). `POST /api/workspaces` requires the workspace and first-project ids for the same reason. Wrapped keys must be v1 base64url envelopes. There is no self-key endpoint to repair a keyless resource. `setupEncryption` runs once per account (409 afterwards); passphrase rotation is separate. `GET /api/user/public-key/:id` returns only `{ id, publicKey }`, and only to that user or somebody who shares a workspace with them (404 otherwise).
- `GET /api/projects/:id/members` is the effective list: explicit grants with `source: 'project'` and `keyStatus`, plus every workspace Owner and Admin once with `source: 'workspace'` (role `admin`, key granted). A workspace has exactly one Owner, enforced by a partial unique index (`member_one_owner_per_workspace`, `WHERE role = 'owner'`; Prisma cannot model it, so it lives in the migration). The Owner is never changed or removed through the member routes. The only way it changes is `POST /api/workspaces/:id/transfer-ownership` (`{ memberId }`, Owner only): the target must hold the workspace key, and one transaction demotes the old Owner to Admin before promoting the target. Account deletion uses the same `WorkspacesService.transferOwnership` primitive.
- An invitation is checked against the signed-in account before anything else happens on the invitee's side: `GET /api/invitations/:id/recipient` (session scope) answers `{ isRecipient }`, and the invite page shows a "different account" notice with a sign-out button instead of the passphrase setup or an accept. The public preview (`GET /api/invitations/:id`) carries only a masked `emailHint` such as `q***@gmail.com`, never the address. Accepting still compares the emails on the server, which stays the authority.
- Notifications (`src/notifications/`, global module): one `notification` table per person (kind, workspace, the stored names as JSON, `readAt`), a CHECK constraint on the six kinds, cascading with the user and the workspace. `NotificationsService` has one method per event (`invitationAccepted`, `accessGranted`, `roleChanged`, `projectRoleChanged`, `removedFromProject`, `removedFromWorkspace`), called by the workspace and project services after the action commits. Recording is best effort and never throws, so a failed notification cannot undo the action. `GET /api/notifications/stream` (`@Sse`) only says "changed" or "ping"; the page reads the lists itself, so nothing about a notification travels on it. The stream lives in one process's memory (documented in "Behind a proxy"). Read notifications are purged after 30 days by the daily cleanup; unread stay. A new notification kind needs the CHECK constraint, the service method, `notification-text.ts` on the frontend, and a test for each.
- `GET /api/projects/:id/assignable-members` (`manage ProjectMember`) is the picker behind "Assign member": workspace members with no grant row on the project (a pending grant is a row, so they are not offered again), never Owners or Admins, as `{ userId, name, email }` only. It exists because a Project Admin who is an Editor in the workspace cannot call `GET /api/workspaces/:id/members`. The project list's own `members` entry (the caller's grant) carries `userId`, which the browser uses to find its own project key.
- `GET /api/access/me` serves the caller's own rules: `canCreateWorkspace`, and — with `?workspace=<id|slug>` — the packed CASL rules for the workspace and for each project role, plus the caller's project grants. It is what the role-aware UI (batch 15) consumes instead of a second rule table.
- `GET /api/workspaces/:id/rekey-queue` (administrators only) is the background re-key's work list, derived from the data with no job table: boards with a payload whose `keyVersion` is behind their project's, oldest first, at most 1000 per call, plus `skippedPublic` for boards with an active public link (they keep their key). The writes are the ordinary payload and file routes.
- There is no global route prefix: each controller declares its full path (`@Controller('api/boards')`, `'api/public/boards'`, …), so new controllers must include `api/` themselves.
- Encrypted payloads go through the API (`PUT/GET /api/boards/:id/payload`, 15MB cap) into `StorageService` (AWS S3 SDK; works with RustFS/MinIO locally and R2/S3 in the cloud).
- Instance limits and trusted proxy (batch 18): `TRUST_PROXY` (`false` by default, integer hop count, or CIDR list) drives Express `trust proxy`; the auth route copies Express's resolved `req.ip` into the `x-canvhq-client-ip` header (replacing any client-sent value) and Better Auth reads the address only from that header, so both always agree and a spoofed `X-Forwarded-For` is ignored unless the setting trusts the hop. Limits default to unlimited: `LIMIT_SIGNUPS_PER_IP` with window `LIMIT_SIGNUPS_WINDOW_SECONDS` (signup attempts recorded in `signup_attempt` table and purged on startup); `LIMIT_WORKSPACES_PER_ACCOUNT` (workspaces the user owns); `LIMIT_BOARDS_PER_ACCOUNT` (boards across owned workspaces); `LIMIT_STORAGE_MB_PER_ACCOUNT` (`Board.payloadBytes` + `SUM(BoardFile.size)` across owned workspaces). All account limits count against the workspace **Owner** (collaborators' work counts against the owner). A refused limit action returns `403 { code: 'LIMIT_REACHED', limit: 'workspaces' | 'boards' | 'storage' | 'signups', message }`. A shrinking payload save is always allowed.
- Demo mode: `DEMO_MODE=true` uses Better Auth's `anonymous` plugin for 1-click throwaway accounts, turns off OAuth providers, and allows production to boot without OAuth. The plugin's own delete-user route is disabled (deleting goes through the normal erasure path). Nightly cleanup is handled by `scripts/demo-wipe.mjs` outside the application (refuses unless `DEMO_MODE=true`, truncates public tables except `_prisma_migrations`, and deletes S3 bucket objects).
- Optional first-account gate: `FIRST_ACCOUNT_EMAIL` (unset by default). While the instance has 0 users, only the configured verified email can register and bootstrap the initial workspace.
- Deleting a board, project, workspace or account is one transaction; every relation in the schema cascades. Stored objects are never deleted on the request path: the transaction writes `pending_blob_deletion` rows (`BlobPurgeService.enqueue(tx, …)`), and `BlobPurgeService` removes the objects in bulk after the commit, on a timer from `@nestjs/schedule`, retrying failures with backoff and never dropping a row silently. Removing a member goes through `WorkspacesService.revokeMembership(tx, …)`. Inside a transaction callback never use `this.prisma`, only `tx`.
- `src/privacy/` currently only purges expired sessions and invitations on startup. The GDPR data export and account erasure live in `users.service.ts`.
- In production, `StaticAssetsModule` serves the built frontend from `./public`; the root `Dockerfile` builds one container that runs both the SPA and the API on port 3000.
- Content Security Policy (CSP) is configured via helmet in `src/app.setup.ts` and computed dynamically from configuration. `script-src` and `connect-src` include the Umami host only when analytics is configured; `font-src` is `'self'`; scripts have no `'unsafe-inline'`.
- Optional operator identity: `OPERATOR_NAME` and `OPERATOR_CONTACT` (email or HTTP/HTTPS URL) configured in env and served via `GET /api/auth/config`.
- What a name may contain is one rule, in `src/common/dto/name.schema.ts` (`thingName` for workspaces, projects and canvases: letters and numbers of any language, spaces and `. , & ( ) _ '`; `personName` for people: starts with a letter, then letters, numbers, spaces and `. ' -`; at most 100 characters, trimmed). Every DTO that takes a name uses it. The browser applies the same rule first (`frontend/src/lib/names.ts`) so the person sees the reason before anything is sent, and the two projects share no code, so `backend/test/names.spec.ts` and `frontend/src/lib/names.test.ts` hold the same table of accepted and refused names: change one, change both. `errorMessage` turns a refused field (a `ZodError`) into its first reason, and `http.ts` does the same for a server validation answer.
- Unit tests stay database-free and mock `PrismaService`; module-level specs sit next to their sources, cross-cutting unit specs are in `backend/test/*.spec.ts`, and real-Postgres integration specs live in `backend/test/integration/*.int-spec.ts` (run via `pnpm -C backend test:integration` with `docker compose up -d db` running, or against `TEST_DATABASE_URL`).

### Frontend (`frontend/`, Vite + React 19)
- UI uses shadcn primitives over one token source (`index.css`), light-only; never write an arbitrary hex class.
- `@/` aliases `src/`. All network requests pass through `src/lib/http.ts` as the single physical `fetch` call site, handling base URL resolution, credentials, explicit `active-organization` header, and typed error mapping (`ApiError`). Feature modules live in `src/features/{workspaces,projects,boards,members,user,public-boards}/` with React-free typed API functions (`api.ts`), Zod schemas validating responses at boundaries (`schemas.ts`), and, for the entities pages read as server state, query keys that carry the workspace id (`keys.ts`) and `useQuery` hooks (`queries.ts`, the only place `useQuery` appears). Pages read through the hooks and write by calling an `api.ts` function, then invalidating the narrowest key (`useQueryClient()`); the current workspace is one query (`useWorkspace`), never copied into page state. Inline `VITE_API_URL` fallbacks and raw `fetch` outside `http.ts` are forbidden and enforced by tests.
- Pages are composition: no page file passes 400 lines. Section components and page-local hooks live in the feature they belong to (`features/<feature>/components/`, `.../hooks/`); features never import from `pages/`. The canvas editor is `features/boards/` (`useBoardSession` composes load, save and the local stash; `board-load.ts`, `board-save-policy.ts` and the one-connection `unsaved-store.ts` live there too). The background re-key is `features/boards/rekey/`: `rekeyBoard` (opens a board with its old key and seals it again with images first, no Excalidraw), `createRekeyRunner` (two boards at a time, three attempts, pause), a thin `rekey.worker.ts` and `useRekeyJob` (starts once per visit for administrators, pause remembered per device). Code the worker loads must not touch `window`, React or the Better Auth client (`lib/api-url.ts` and `lib/crypto.ts` use the global `location`/`crypto` for that reason; `getHomeWorkspaceSlug` lives apart from `workspaces/api.ts`). Server state is never copied into `useState`, and a `useEffect` never fetches. Loading and failure use `LoadingState`/`ErrorState`; `AppErrorBoundary` wraps the router and `CanvasErrorBoundary` the canvas. A `catch` on a user action toasts or shows an inline error, or says in a comment why silence is right.
- Tests stub `fetch` with real `Response` objects from `src/test/http.ts` (`jsonResponse`, `errorResponse`, `emptyResponse`, `networkFailure`); `http.ts` has no branches for fake responses. Each user mutation has a test where the server refuses and the user sees why. Components never call `crypto.subtle` or wrap/unwrap keys; that is `lib/keys`.
- Auth client is `src/lib/auth-client.ts` (Better Auth). Role-aware UI reads the server's rules from `GET /api/access/me` through `useAccess`; the UI never compares role strings to gate an action. Routes/pages live in `src/pages/`; every page and component has a colocated `*.test.tsx`.
- All key work happens in the framework-free `src/lib/keys/` service, which either returns the key or throws a typed `KeyServiceError` (`locked`, `no-public-key`, `no-workspace-key`, `no-project-key`, `wrap-failed`, `unwrap-failed`). `KeyContext` only keeps identity state (the unlocked private key, the public key, set-up status). The passphrase comes first: an authenticated user without an identity key is redirected to `/setup-passphrase?next=…` before any other protected page, including `/create-workspace` and invitation acceptance. Boards never carry their key in an internal URL or in `localStorage`; only the public share link puts a key in its fragment. Every sign-out path clears the cached private key and any legacy `canvhq_key_*` entries.
- Nothing loads from a third-party origin at run time. Excalidraw's fonts are copied into the build (`vite.config.ts`, `/excalidraw-assets/`), `public/excalidraw-config.js` points Excalidraw at them before any module runs (an inline script is not allowed by the policy), and a build plugin repoints Excalidraw's built-in CDN fallback at our copy and fails the build if that line changes. `bootstrap.ts` turns off Zod's start-up `Function` probe, which the policy would report. `e2e/production-image.spec.ts` (a whole visitor journey, with no violation allowed) checks all of this against the production image in demo mode (`pnpm run test:e2e:image`, see `e2e/README.md`; it also runs the multi-user key-flow specs there with demo accounts, `E2E_DEMO_SESSIONS`).
- Saving a canvas: the canvas opens only from a board record fetched after the page mounted (`useBoard` has `staleTime: 0`, `BoardCanvas` waits for `isFetchedAfterMount`), because the cached revision and `hasPayload` go stale the moment the board is saved. `useBoardSave` takes what was loaded (or an empty canvas for a board never saved) as the baseline, so nothing is written until the person edits, and a board opened again starts clean. Anything but "saved" is unsaved work: the browser's leave prompt and an in-app `useBlocker` dialog (`BoardLeaveDialog`) both guard it. `useBlocker` needs a data router, so `main.tsx` uses `createBrowserRouter` with one catch-all route, and tests render under `src/test/data-router.tsx`. A copy kept on this device is opened with `openStashedScene` (its own header decides, no rollback check) and merged into the open scene, never replacing it. `e2e/canvas-saving.spec.ts` covers all of this in a browser.
- What a person cannot do is not shown to them: no disabled buttons or links to screens they cannot use, and a guessed address is refused too. Workspace Management is for Owners and Admins only: the nav links check `isAdministrator`, and `WorkspaceAdminRoute` sends anyone else to the workspace home with a reason. `useAccess` returns no rights (not "loading") when the server will not describe the workspace. A new control or route takes its visibility from `useAccess`, with a test for the roles that must not see it (`e2e/role-ui.spec.ts` covers an editor in a real browser). Project access has a second door: "Add members" beside "New Canvas" opens `ProjectAccessModal` for whoever `can('manage', 'ProjectMember')` on that project, which is how a Project Admin who is only a workspace Editor manages their project (`e2e/project-admin-members.spec.ts`). The dialog never reads the workspace member list (that is Owner/Admin only); it asks the project for `assignable-members`. A Project Admin cannot re-key, so after a removal the dialog tells them an Owner or Admin's next visit will.
- Notifications (`features/notifications/`): the bell sits in `AppHeader`; `NotificationUpdates` (mounted once in `App`) keeps one `EventSource` open while signed in and, when told "changed" (and again after a reconnect, and when a notification is opened), runs `refreshAfterNotification`: the inbox, but also the workspaces, rights, projects and members, because a notification means the person's access changed and the page they land on must not be a stale one. The two queries read again on window focus (`staleTime: 0`), which is the way back when the stream is down. Sentences are built in `notification-text.ts` from the stored names; a kind or details it does not recognise shows a plain fallback sentence. `e2e/notifications.spec.ts` covers the live path in a browser.
- Analytics route safety: Umami is never loaded on `/share/:token` or `/w/:slug/canvas/:boardId` (or any canvas route); where loaded, it carries `data-exclude-hash="true"` and `data-do-not-track="true"`.
- Copy rules: Never use absolute claims or security superlatives. Say what is encrypted (canvas elements and images) and what is not (names, emails, memberships, metadata). Recovery is a fact: "We cannot reset your passphrase. If you lose it, your canvases cannot be opened." Third parties are never described with pricing or marketing claims.
- Anything that changes who can open or edit a canvas (roles, grants, invitations, removal, key rotation, hand-over, account erasure) gets its event added to a journey built on `e2e/rbac-cast.ts` (`rbac-*.spec.ts`), which re-checks every canvas ever made for every person after each step; a single-step test is not enough, as the canvas-after-rotation bug showed.
- Playwright specs in `e2e/` cover E2EE flows, auth, and workspace isolation. They log in through the backend's `POST /api/auth/dev-login` (requires `ENABLE_DEV_LOGIN=true` to be switched on in `.env`) and drive the passphrase-setup page via helpers in `e2ee-test-helpers.ts`. Run them with `pnpm run test:e2e` (origins from `E2E_BASE_URL`/`E2E_API_URL`, default `localhost`; needs `RATE_LIMIT_ENABLED=false`; `e2e/README.md` has the prerequisites).

### Gotchas
- A board's key generation is its project's: the server stores the project's `keyVersion` on the board, the browser opens the board with that number, so `provisionBoardKeys` seals a new canvas with the project's current version (it takes no separate board version). Sealing as version 1 after a rotation once made every later canvas unopenable; `e2e/canvas-after-rotation.spec.ts` creates and reopens canvases across two rotations.
- Rate limiting is controlled solely by `RATE_LIMIT_ENABLED` (not `NODE_ENV`), and that includes Better Auth's own sign-in limiter (3 sign-ins per 10 seconds per address, counted from the last request), which `createAuth` ties to the flag; before it did, a burst of demo sign-ins from one address made the image suite fail now and then with "Too many requests". The integration test harness disables it by default and enables it explicitly in `rate-limit.int-spec.ts`. The local `docker compose` stack also defaults it to `false`, because every Playwright context shares one IP; the production image keeps the schema default (`true`).
- `pnpm` needs `allowBuilds` approval for packages with install scripts, and it reads its settings from `pnpm-workspace.yaml` only — not from `.npmrc`, and not from the `pnpm` field in `package.json`. The backend needs `@prisma/client`, `@prisma/engines` and `prisma` approved; the frontend needs `publicHoistPattern: ['*roughjs*']`, because Excalidraw imports `roughjs/bin/rough` and the alias in `vite.config.ts` points at a hoisted path.
- Licence and notices: Apache-2.0 (`LICENSE`, `NOTICE`, and the `license` field of all three `package.json` files). `npm run build` in `frontend/` also writes `dist/THIRD_PARTY_LICENSES.txt` from the installed production dependencies (`scripts/third-party-licenses.mjs`); the Terms page links to it. The bundled AWS icon set is gone, and Mermaid loads only when a diagram is imported.
- Docs live in `frontend/src/docs/articles/` and are checked by tests: every setting in `backend/src/config/env.schema.ts` must be in the environment variables article, the compose file in "Run with Docker Compose" must equal `docker-compose.prod.yml`, internal links must resolve, and `src/lib/copy.test.tsx` scans them for banned wording. `validateEnv` treats an empty value as not set, because compose passes unset variables through as empty strings.
- CI (`.github/workflows/ci.yml`) runs format, types, lint, unit, integration (Postgres and an S3-compatible service), the browser suite and the production image. `docker-publish.yml` calls it first, boots the image with `scripts/smoke-test-image.sh` (real entrypoint, demo mode, fails on a non-zero exit, a missing health answer or a missing CSP), and publishes immutable tags (commit, version); `latest` only for a release tag.
- The `pnpm-lock.yaml` files contain pnpm's own platform binaries, because `packageManager` pins the pnpm version. That is expected; do not strip it.

## Working agreements

- A bug fix comes with a regression test that fails before the fix and passes after it. Data-integrity tests run against a real Postgres, not a mocked Prisma client.
- Commit in meaningful chunks rather than one commit per change, and keep going until the agreed task is finished rather than stopping to ask for a check-in at every step.
- No AI attribution in commit messages, code, comments, docs or issues.
- Update `local/docs/canvhq_prd.md` when behaviour it describes changes.

## Audit batches

Work from the audit is issued as batches. `local/audit-batches.md` is the index of all of them; `local/audit-batch-current.md` is the one that is active, and it is a self-contained brief with the scope, the acceptance criteria and a checklist.

- **The coder works from `local/audit-batch-current.md` and nothing else.** The batch file is the contract. If something is not in it, it is not in scope — note it in the Review log instead of doing it.
- Tick items in the checklist as you complete them.
- **The Review log at the bottom of the batch file has two parts.** Under "Coder's verification run" you paste the real output of every acceptance command and note anything out of scope. The reviewer's entries ("Review 1", …) are theirs; leave them alone.
- The reviewer runs the acceptance criteria independently, records what was actually observed, and lists anything that must change as unchecked boxes in the same file.
- A batch is closed only when the reviewer says so. Then `local/audit-batches.md` moves it to done and the next batch is opened.

## Planning docs

Planning docs live in the git-ignored `local/` folder and may not exist in every checkout. Put new audits, plans and similar working docs there too, never in the committed tree.
